# AI 对话历史、人设与上下文缓存设计

## 背景

当前统一 AI 对话框已经完成了两阶段路由：

- 第一阶段做轻量意图识别。
- 第二阶段按意图进入闲聊、补记或添加待办。

但聊天层目前仍有三个明显缺口：

1. 对话历史仍按“当天一个本地 key”保存，不是真正的会话模型。
2. 聊天人格仍是固定 prompt，没有会话级人设。
3. 没有可控的上下文缓存，正式请求仍基本按单轮模式发送。

这会导致几个问题：

- 用户无法明确管理多条对话流。
- 关闭重开后虽然能恢复消息，但缺少“当前会话 / 历史会话 / 新建会话”的明确模型。
- AI 在连续聊天场景里无法根据最近几轮上下文持续理解用户。
- 不同风格的人设需求无法在聊天入口快速切换。

## 目标

- 将统一 AI 对话框升级为真正的“会话制聊天”。
- 默认始终进入同一条最近活跃会话。
- 只有用户主动打开历史对话并点击“新建对话”时才创建新会话。
- 支持会话级 AI 人设，包含头像、名字、称呼、自定义提示词和上下文条数。
- 提供几套可快速切换的预设人设。
- 增加“快速上下文”开关，开启后把最近 `n` 条消息一起发给 AI 理解。

## 非目标

- 本次不做云同步聊天记录。
- 不做聊天记录全文检索。
- 不做复杂的人设市场或导入导出。
- 不在本次中把 AI 设置页里的 API 配置和聊天人设合并到同一个页面。

## 已确认的交互前提

- 历史对话采用“全局会话列表”，不是按日期分组。
- 默认都在一个对话流中。
- 只有用户点击历史对话时，才能主动新建一个对话。

## 方案对比

### 方案 A：全局会话列表 + 最近活跃会话

优点：

- 最符合聊天产品直觉。
- 和“默认始终同一条流”完全一致。
- 人设和上下文缓存都可以自然挂在会话上。

缺点：

- 需要把当前“按天存储”重构成“按会话存储”。

### 方案 B：按日期分组的多会话历史

优点：

- 更接近当前实现方式。

缺点：

- 会话容易被日期切断。
- 用户难理解“默认同一条流”的真实含义。

### 方案 C：单一主会话 + 手动归档

优点：

- 交互最简单。

缺点：

- 后面想做多条工作流、人设分流、上下文缓存管理会受限。

### 结论

采用方案 A。

## 会话模型

新增本地存储模型 `ai chat sessions`：

```ts
interface AIChatSession {
  id: string;
  title: string;
  createdAt: number;
  updatedAt: number;
  personaId: string;
  contextCacheEnabled: boolean;
  messages: ChatMessage[];
}
```

同时增加一个单独的当前指针：

```ts
interface AIChatSessionState {
  activeSessionId: string | null;
  sessions: AIChatSession[];
}
```

## 会话规则

### 默认进入规则

- 打开 AI 对话框时，优先进入最近活跃会话。
- 如果本地还没有任何会话，则创建一条默认会话。

### 新建规则

- 不因为跨天自动新建。
- 不因为关闭重开自动新建。
- 不因为切换人设自动新建。
- 只有在历史面板里点击“新建对话”时才新建新会话。

### 会话标题

- 会话初始标题为“新对话”。
- 当该会话收到第一条用户消息后，自动用该消息前若干字生成标题。
- 本次先不做人手重命名入口。

## 聊天头部改造

### 右上角按钮

当前右上角“删除/清空”按钮改为“历史对话”按钮。

行为：

- 点击后打开历史会话面板。
- 面板中提供：
  - 会话列表
  - 当前会话高亮
  - 新建对话按钮
  - 切换会话

### 清空历史行为

不再在主界面提供“一键清空当前消息”按钮。

如果后续需要清理能力，可以放到历史面板内再补“删除会话”，但本次不作为必需项。

## AI 人设模型

新增会话级 persona 配置：

```ts
interface AIChatPersona {
  id: string;
  name: string;
  avatarIcon: string;
  assistantSelfName: string;
  userCallName: string;
  systemPrompt: string;
  contextMessageLimit: number;
  isBuiltIn: boolean;
}
```

## 人设交互

### 入口

- 点击标题栏左侧 AI 头像，打开“AI 人设”面板。

### 人设面板内容

- 当前人设名称
- 图标选择
- AI 自称
- 对用户的称呼
- 自定义提示词
- 最近上下文条数 `n`
- 预设列表

### 预设

内置几套：

1. 默认助理
   - 偏克制、执行导向。
2. 温柔陪伴
   - 偏支持、缓和、安抚。
3. 严谨规划
   - 偏澄清、拆解、结构化。
4. 轻松聊天
   - 偏自然聊天、少工具感。

### 会话与人设关系

- 每个会话记录一个 `personaId`。
- 新会话默认继承当前活动会话的人设。
- 切换会话时自动恢复该会话对应人设。

## 上下文缓存

### 快速开关

在聊天标题栏提供一个快速上下文开关。

行为：

- 关闭：正式执行阶段只发送当前用户消息。
- 开启：正式执行阶段额外附带最近 `n` 条消息摘要。

### `n` 的来源

- `n` 由当前会话的人设字段 `contextMessageLimit` 决定。
- 人设面板中可以修改。

### 作用范围

只作用于第二阶段正式执行：

- 闲聊正式回复
- 添加补记正式执行
- 添加待办正式执行

不作用于第一阶段意图识别。

这样可以保证分类阶段仍然轻量、稳定。

## 上下文缓存内容

缓存时不直接把完整消息 JSON 发送给模型，而是提炼为简洁消息序列：

```ts
interface AIChatContextTurn {
  role: 'user' | 'assistant';
  content: string;
}
```

选择规则：

- 只取最近 `n` 条消息。
- 仅使用消息正文 `content`。
- 不带调试数据。
- 不直接带完整工具调用原始 JSON。
- 应用结果如果需要进入上下文，只通过最终回复文本体现。

这意味着：

- AI 看到的是自然对话历史。
- 不会把本地实现细节和调试结构污染进 prompt。

## Prompt 组装策略

### 第一阶段：意图识别

继续使用短固定 prompt，不拼人设、不拼上下文缓存。

原因：

- 防止人设影响分类结果。
- 控制成本和时延。

### 第二阶段：正式执行

统一组装顺序：

1. 固定任务 prompt
2. 当前 persona 的风格 prompt
3. 可选的最近 `n` 条上下文消息
4. 当前业务上下文
5. 当前用户输入

## 服务层改造

`aiService.ts` 需要增加 persona/context 参数支持，但保持原有职责边界：

- `classifyChatIntentWithDebug`
  - 不接 persona/context cache
- `sendContextualChatReplyWithDebug`
  - 接 persona prompt + context turns
- `planBackfillToolCallsWithDebug`
  - 接 persona prompt + context turns
- `planTodoToolCallsWithDebug`
  - 接 persona prompt + context turns

这部分可以通过新增可选参数完成，避免再次复制三套近似逻辑。

## 组件层改造

`AIBackfillChatModal.tsx` 需要从“单会话消息数组”提升为“会话容器”：

### 新状态

- `sessions`
- `activeSessionId`
- `isHistoryPanelOpen`
- `isPersonaPanelOpen`
- `personas`

### 当前消息来源

- `messages` 不再直接作为顶层状态单独保存。
- 当前显示内容来自 `activeSession.messages`。

### 更新行为

- 用户发消息、AI 回消息、工具应用结果，都只更新当前会话。
- 每次更新同步刷新 `updatedAt`。

## 存储策略

### 会话与人设本地存储

建议新增本地 key：

- `lumostime_ai_chat_sessions_v1`
- `lumostime_ai_chat_active_session_v1`
- `lumostime_ai_chat_personas_v1`
- `lumostime_ai_chat_debug_mode_v1`

### 迁移策略

当前旧实现使用按天 key：

- `lumostime_ai_backfill_chat_v2_<date>`

本次不强做复杂迁移。

处理方式：

- 新版本首次进入时，如果没有新会话数据，则创建默认会话。
- 旧按天记录不自动导入。

理由：

- 当前新聊天模型变化较大。
- 旧记录缺少会话级 persona 和缓存开关信息。
- 为了避免导入出错，本次优先保证新模型稳定。

## UI 结构建议

### 历史面板

建议使用右侧滑出面板，而不是全屏跳转。

优点：

- 不打断当前聊天心流。
- 和“从右上角打开历史”更匹配。

内容：

- 顶部标题“历史对话”
- 新建对话按钮
- 会话列表
- 当前会话高亮

### 人设面板

建议使用从顶部标题区触发的全屏设置面板或底部抽屉。

优先推荐全屏设置面板，因为字段较多：

- 头像
- 名称
- 称呼
- prompt
- 上下文条数
- 预设

## 测试与验证

至少验证：

1. 首次进入会自动创建一条默认会话。
2. 关闭重开后仍回到同一会话。
3. 历史面板可切换旧会话。
4. 只有点击“新建对话”才创建新会话。
5. 点击 AI 头像可打开人设面板。
6. 切换预设后会影响正式回复风格，但不影响意图识别。
7. 快速上下文关闭时，只发送当前用户输入。
8. 快速上下文开启时，会带最近 `n` 条对话。
9. `n` 修改后，正式请求上下文数量随之变化。
10. 补记和待办流在开启上下文缓存后仍能正常工具应用。
11. 调试模式仍能展示两阶段请求。
12. 构建通过。

## 风险与控制

### 风险 1：会话状态重构引入回归

控制：

- 把消息渲染层尽量保持不变，只替换其数据来源。

### 风险 2：上下文缓存让 prompt 膨胀

控制：

- 只缓存最近 `n` 条。
- 默认值设得保守。
- 只缓存纯文本消息。

### 风险 3：人设干扰工具规划

控制：

- 第一阶段不受人设影响。
- 第二阶段人设只作为风格层附加，不替代任务约束。

### 风险 4：旧按天记录无法平滑继承

控制：

- 本次明确不做复杂迁移。
- 新模型上线后从统一会话流开始积累。
