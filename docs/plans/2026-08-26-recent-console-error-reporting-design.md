# Recent Console Error Reporting Design

## Goal

Let a user manually send the most recent renderer warnings and errors to Sentry so support can diagnose failures without asking the user to open developer tools and copy logs.

## Architecture

- Extend `src/services/errorReporting.ts` with an in-memory ring buffer.
- Install the capture hooks from the existing `initializeErrorReporting()` entry point before React mounts.
- Capture `console.error`, `console.warn`, `window.error`, and `unhandledrejection`; preserve the original console behavior.
- Keep the most recent 30 records and cap the serialized report size. Do not include normal `console.log` output.
- Add `reportRecentConsoleErrors()` to sanitize and send a single Sentry message with the buffered records as diagnostic context.
- Add a Settings action that invokes the helper only after an explicit user click.

## Privacy and Failure Handling

- Sanitize common secrets (`password`, `token`, `secret`, `authorization`, `cookie`, `apiKey`) and URL query parameters.
- Do not include local storage, sync configuration, user data snapshots, or complete request bodies.
- Handle `Error`, objects, multiple console arguments, and circular references without throwing.
- When Sentry is disabled, do not make a network request. When sending fails, keep the buffer and show a failure toast.
- Avoid recursive capture of errors generated by the reporting action itself.

## UI

Add a concise `发送错误日志` action in the Settings main screen. The action reports one of: success with the Sentry event ID, no configured diagnostics service, no buffered errors, or upload failure.

## Verification

- Unit-test buffer limits, serialization, secret and URL sanitization, event/rejection capture, and reporting-disabled behavior.
- Build with `npm run build` and smoke-test the Settings action with Sentry enabled and disabled.
