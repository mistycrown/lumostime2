# 图片清理补充投喂设置引用设计

## 背景

当前“数据管理 -> 图片管理”中的“检查未引用图片”和“执行清理”主要基于两类引用来源判断图片是否仍在使用：

- 专注详情中的 `log.images`
- 待办中的 `todo.coverImage`

这个口径不完整。投喂功能中的部分自定义图片同样属于“用户正在保留和使用的素材”，不应该被判定为未引用图片，更不应该在清理时被删除。

已确认的投喂设置图片来源中：

- 自定义时间小友图片会通过 `imageService.writeImage()` 落到本地图片仓库，当前会被误判为未引用
- 自定义背景当前存储为 `localStorage` 中的 data URL，不在 `imageService.listImages()` 返回的图片仓库中，因此当前逻辑实际上不会把它删除

本次设计目标是修正“图片仓库内的设置图片引用识别”，并把规则组织成可扩展结构，避免未来新增设置图片入口时再次遗漏。

## 目标

- 检查未引用图片时，把投喂功能中的已上传自定义图片视为“已使用”
- 执行清理时，保护这些图片，不将其删除
- 检查未引用图片与执行清理时，使用扩展后的保护口径
- 采用“保护所有已上传的设置图片素材”的规则，而不是只保护当前选中的图片

## 非目标

- 不修改自定义背景的存储方式
- 不改变现有图片删除流程
- 不对 WebDAV / 远程同步策略做额外扩展
- 不新增 UI 入口或提示文案

## 方案选型

### 方案 A：统一补充设置层引用来源

在图片清理中，除了业务数据引用，还统一采集设置层的图片引用；但云同步图片列表仍保持独立口径。

优点：

- `检查未引用图片`、`执行清理` 可以统一扩展保护口径
- 后续新增其他设置图片时，只需在统一入口补充采集逻辑
- 语义清晰，便于维护

缺点：

- 需要明确区分“清理保护”与“同步列表”两种用途

### 方案 B：仅在图片清理中对自定义时间小友做特判

优点：

- 改动最小

缺点：

- `修复图片列表` 仍会漏掉这类图片
- 规则分散，后续扩展成本高

### 方案 C：按文件名前缀兜底保留

优点：

- 实现最快

缺点：

- 规则脆弱
- 无法表达真正的“引用来源”

### 结论

采用方案 A，但拆分为两套口径：

- 清理保护口径：业务数据引用 + 设置素材引用
- 同步图片列表口径：仅业务数据引用

## 设计

### 引用来源模型

图片引用分为两层：

1. 业务数据引用
- `logs[].images`
- `todos[].coverImage`

2. 设置素材引用
- `timePalCustomService.getAllItems()` 中每个自定义时间小友的 `stageFilenames`

说明：

- 自定义背景虽然属于“设置素材”，但当前不进入图片仓库，不参与 `imageService.listImages()` 对比
- 设计上保留“设置素材引用”这一层，便于后续继续纳入新的图片来源

### 代码结构调整

#### `src/services/imageCleanupService.ts`

- 新增一个专门的方法用于收集设置层图片引用
- 聚合为统一的 `referencedImages` 集合
- `checkUnreferencedImages()`、`cleanupUnreferencedImages()`、`getImageUsageStats()`、`generateCleanupReport()` 继续基于统一引用结果工作

建议结构：

- `getReferencedImages(logs, todos)`：总入口
- `getSettingsReferencedImages()`：设置层引用入口

#### `src/services/imageService.ts`

- 当前 `collectReferencedImages()` 和 `rebuildReferencedListFromLogs()` 只覆盖日志和待办
- 保持该行为，不把设置素材引用写入图片列表
- 原因是图片列表会参与云端图片上传决策，而自定义时间小友不参与云同步

### 规则细节

- 自定义时间小友的全部 `stageFilenames` 都视为“清理保护中的已使用”
- 不区分该自定义小友是否当前被选中
- 只处理字符串类型且非空的文件名
- 对应缩略图按现有规则一并加入引用集合
- 这些文件不进入 `lumos_referenced_images`

### 错误处理

- 若 `TIMEPAL_KEYS.CUSTOM_ITEMS` 中存在损坏数据，跳过非法文件名，不中断整个流程
- 不修改现有图片删除的异常处理逻辑

## 影响范围

- `src/services/imageCleanupService.ts`
- `src/services/imageService.ts`
- `docs/plans/2026-03-16-image-cleanup-settings-reference-design.md`

## 验证方案

1. 创建一个自定义时间小友并上传 5 张图片
2. 在数据管理页面执行“检查未引用图片”
3. 确认这 5 张图片及其缩略图不出现在待清理结果中
4. 执行“修复图片列表”后，确认引用列表不包含这些图片
5. 执行同步上传时，确认这些图片不会被纳入上传集合
6. 执行“执行清理”后，确认自定义时间小友仍可正常预览和使用
7. 再准备一张未被日志、待办、设置引用的普通图片，确认它仍会被识别并清理

## 风险

- 现有“被引用图片数量”统计仍然是按文件层级统计，加入设置素材后数字会增大，这是符合新口径的结果
- 若后续新增其他设置图片来源但未接入统一入口，仍可能再次出现遗漏，因此后续应继续沿用该结构扩展
