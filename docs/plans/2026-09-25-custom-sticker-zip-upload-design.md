# 自定义贴纸压缩包上传设计

## 目标

在“Sticker 集”现有“新建”入口旁增加“从压缩包上传”按钮。用户选择一个 ZIP 后，应用读取其中的一个或多个文件夹，将每个文件夹导入为一个自定义贴纸组。

每个文件夹最多导入 16 张图片：图片按压缩包内路径排序后取前 16 张；超过部分不导入，并在结果提示中说明。每组少于 16 张时按实际数量导入。

## 方案

采用纯前端直接导入方案，复用现有 `jszip`、`imageService` 和自定义贴纸状态链路。无需新增服务端或 Electron 专用处理逻辑，Web、Android 和桌面端可以共享同一套实现。

## 解析与分组

1. 新增隐藏文件输入，接受 `.zip` 文件；入口按钮位于“新建”按钮旁。
2. 使用 `JSZip.loadAsync` 读取 ZIP。
3. 仅处理文件条目，不处理目录条目；根据图片扩展名或 MIME 类型筛选 PNG、JPG、JPEG、WEBP、GIF、BMP 等常见图片。
4. 使用图片条目的直接父文件夹作为分组键。没有父文件夹的根目录图片和非图片文件忽略。
5. 每组按条目完整路径排序，取前 16 个图片条目。图片文件名去掉扩展名后作为贴纸标签。
6. 文件夹名作为贴纸组名称。若名称与已有自定义组重复，自动追加 ` (2)`、` (3)` 等后缀，避免覆盖现有组。

## 导入数据流

对每个有效文件夹执行以下步骤：

1. 创建新的 active `CustomStickerSetRecord`，记录组名、时间和空的 `stickerIds`。
2. 将 ZIP 条目转换为 `File`/`Blob`，逐张调用 `imageService.saveImage(file, 'theme')`，保存原图和缩略图。
3. 为每张图片创建 active `CustomStickerRecord`，使用 0～15 的 `sortOrder`，并把记录 ID 写入组的 `stickerIds`。
4. 组内全部图片成功后，将组记录和贴纸记录写入 `SettingsContext` 状态。
5. 触发已有状态持久化、图片清单和贴纸变更事件。

为避免保存状态指向缺失图片，元数据只在该组图片全部保存成功后提交。若组内任一图片保存失败，删除该组已经保存的图片，并放弃该组元数据；其他组继续导入。

## 用户反馈与错误处理

- 未选择文件、取消选择：不提示错误。
- ZIP 无法读取：提示“压缩包读取失败”。
- ZIP 中没有有效文件夹图片：提示“压缩包中没有可导入的贴纸图片”。
- 文件夹超过 16 张：照常导入前 16 张，并在完成提示中列出截取数量。
- 某组导入失败：该组回滚并在完成提示中列出失败组名；其他成功组保留。
- 导入过程中按钮禁用，避免并发导入导致状态和槽位冲突。

## 不在本次范围内

- 不新增预览确认弹窗。
- 不导入 ZIP 根目录散落的图片。
- 不修改现有单张上传、贴纸选择器或自定义贴纸数据结构。
- 不改变已有导出、同步和图片清理逻辑；导入后的记录自然复用这些能力。

## 验证标准

1. 入口旁可打开 ZIP 文件选择器，导入一个文件夹后出现同名贴纸组。
2. 一个 ZIP 内多个文件夹分别生成多个贴纸组。
3. 1～16 张图片的文件夹按实际数量导入并占用对应槽位。
4. 超过 16 张时只导入排序后的前 16 张，并给出截取提示。
5. 非图片文件、根目录图片不会生成贴纸。
6. 同名文件夹不会覆盖已有组，会生成带序号的组名。
7. 单组图片保存失败时该组图片文件被清理，其他组仍可用。
8. 导入的贴纸可以在现有选择器中查看、选择、刷新后继续显示，并参与现有导出/同步状态。
