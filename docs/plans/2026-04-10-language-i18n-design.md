# 语言切换与渐进式国际化设计
日期：2026-04-10

## 目标
在不大范围扰动现有仓库的前提下，为 LumosTime 增加“中文 / English”语言切换能力，并满足以下要求：

- 用户在偏好设置切换语言后立即生效，无需重启应用。
- 第一阶段只迁移偏好设置页及少量公共文案，不做全库一次性替换。
- 为后续渐进式迁移建立稳定、低维护成本的国际化基础设施。
- 未迁移页面在过渡期内继续可用，不因为缺失翻译而显示异常。

## 非目标
- 第一阶段不追求全应用 100% 中英切换完成。
- 第一阶段不引入重量级国际化库。
- 第一阶段不批量清扫所有硬编码中文 / 英文文案。
- 第一阶段不调整业务逻辑，仅建立语言状态和文本读取通道。

## 背景与约束
- 仓库体量较大，页面和组件数量多，文案分散在多个视图、组件、Toast、Alert 与服务提示中。
- 当前存在中英混杂的界面文本，问题不在于“缺少一个语言选项”，而在于“缺少统一文案出口”。
- 仓库中已经预留语言存储键：`SETTINGS_KEYS.LANGUAGE = 'lumostime_language'`，适合作为持久化入口。
- 当前设置体系由 `SettingsContext` 统一管理，适合作为响应式语言状态承载点。
- 用户明确要求切换语言后“立刻生效”，因此语言必须进入 React 状态，而不是仅写入 `localStorage`。

## 方案对比

### 方案 A：轻量自研 i18n 层
做法：
- 在 `SettingsContext` 中新增语言状态。
- 在 `src/i18n/` 中维护语言字典与轻量 `t()` 翻译函数。
- 组件通过 Hook 读取当前语言并返回对应文案。

优点：
- 与现有仓库耦合低，改造范围可控。
- 没有额外依赖，便于逐步迁移。
- 容易定制“缺失翻译回退中文”的过渡行为。

缺点：
- 需要自行维护字典结构与一致性校验。

结论：
- 作为第一阶段推荐方案。

### 方案 B：引入 `react-i18next`
做法：
- 安装依赖并按生态方式组织 namespace、provider、hook。

优点：
- 生态成熟，插值、复数、命名空间等能力完整。

缺点：
- 对当前需求偏重。
- 初次接入成本更高，第一阶段收益不明显。

结论：
- 可作为未来升级路径，但不适合作为当前最小风险方案。

## 决策
采用“轻量自研 i18n 层 + 渐进式迁移”的方式。

第一阶段只覆盖：
- 全局语言状态。
- 偏好设置中的语言切换入口。
- 偏好设置页自身文案。
- 少量公共文案与演示性翻译链路。

其余页面保持现状，后续按“碰到再迁移”的策略逐步转入国际化体系。

## 第一阶段范围

### 包含
- 在 `SettingsContext` 中增加：
  - `language: 'zh-CN' | 'en-US'`
  - `setLanguage`
- 从 `SETTINGS_KEYS.LANGUAGE` 读取默认语言并持久化保存。
- 新建轻量语言目录，例如：
  - `src/i18n/locales/zh-CN.ts`
  - `src/i18n/locales/en-US.ts`
  - `src/i18n/index.ts`
  - `src/hooks/useI18n.ts`
- 在偏好设置页新增“语言”配置项。
- 切换语言后立即刷新偏好设置页文案。
- 为缺失翻译提供中文回退。

### 不包含
- 全局一次性替换所有视图、组件、服务、Toast 文案。
- 文档、用户指南、导出模板、图片文本等非 UI 主链路内容的翻译。
- 大规模改造日期格式、排序规则、原生插件文案。

## 架构设计

### 1. 语言状态层
在 `SettingsContext` 中托管全局语言状态：

- 初始化优先级：
  1. `localStorage` 中的 `SETTINGS_KEYS.LANGUAGE`
  2. 默认值 `zh-CN`
- 对外暴露：
  - `language`
  - `setLanguage`
- 在 `useEffect` 中将最新语言写回本地存储。

这样语言变化会触发所有消费该状态的组件重新渲染，从而实现立刻生效。

### 2. 翻译字典层
为中英文分别维护结构一致的字典对象：

```ts
export const zhCN = {
  settings: {
    preferences: {
      title: '偏好设置',
      language: {
        label: '语言',
        description: '切换应用界面语言',
        zhCN: '简体中文',
        enUS: 'English'
      }
    }
  }
};
```

```ts
export const enUS = {
  settings: {
    preferences: {
      title: 'Preferences',
      language: {
        label: 'Language',
        description: 'Change the app interface language',
        zhCN: '简体中文',
        enUS: 'English'
      }
    }
  }
};
```

命名规则：
- 以模块分组，例如 `settings.preferences.title`
- 避免 `text1`、`labelA` 之类弱语义 key
- 保持中英结构镜像一致

### 3. 翻译访问层
提供一个轻量 `t()` 访问函数和 `useI18n()` Hook。

职责：
- 根据当前 `language` 选择字典。
- 支持通过点路径读取文案，例如 `t('settings.preferences.title')`
- 若目标语言缺失，则回退到中文。
- 若中文也不存在，则返回 key 并在开发环境打印警告。

第一阶段只需支持最基础的字符串查找；插值能力可以以最小实现保留扩展位。

### 4. 视图接入层
偏好设置页改造方式：
- 现在的硬编码字符串改为 `t(...)`
- 新增“语言”设置项，调用 `setLanguage('zh-CN')` / `setLanguage('en-US')`
- 使用当前 `language` 决定选中态

这样偏好设置页本身可以成为第一块被完整接入国际化系统的页面。

## 数据流
用户在偏好设置页切换语言后的链路：

1. 用户点击语言按钮。
2. `PreferencesSettingsView` 调用 `setLanguage('en-US')`。
3. `SettingsContext` 更新 `language` 状态。
4. 订阅该状态的 `useI18n()` 重新选择英文词典。
5. 使用 `t(...)` 的组件重新渲染并显示英文。
6. `useEffect` 将新语言写入 `localStorage`。
7. 下次启动时从持久化状态恢复语言。

## 迁移策略

### 迁移原则
- 不全库一次性替换。
- 新增文案必须进入语言包。
- 修改到的旧文件顺手迁移，不要求一次清仓。
- 未迁移页面允许继续使用旧文案，直到被纳入后续阶段。

### 建议阶段

#### 阶段 1：打底
- 接入语言状态。
- 建立 `t()` 与语言字典。
- 完成偏好设置页语言切换。
- 仅迁移偏好设置页及极少量公共文案。

#### 阶段 2：公共壳层
- 设置主页面标题与入口文案。
- 底部导航与常用按钮。
- 常见 Toast / Alert。

#### 阶段 3：高频业务页
- 记录页
- 待办页
- 时间脉络页
- 档案 / 索引等主导航页面

#### 阶段 4：长尾与格式化
- 空状态文案
- 帮助性说明
- 日期、周几、格式化文本
- 服务层提示

## 维护策略

### 字典组织
不建议把所有文案堆在一个大文件中，建议按模块拆分，例如：

- `src/i18n/locales/zh-CN/common.ts`
- `src/i18n/locales/zh-CN/settings.ts`
- `src/i18n/locales/zh-CN/navigation.ts`
- `src/i18n/locales/en-US/common.ts`
- `src/i18n/locales/en-US/settings.ts`
- `src/i18n/locales/en-US/navigation.ts`

再由各语言入口文件统一聚合导出。

### 缺失翻译回退
为了支持渐进迁移，`t()` 应采用：
- 目标语言缺失 -> 回退中文
- 中文也缺失 -> 返回 key

这样不会因为英文词典尚未补齐而导致页面崩溃或显示空白。

### 动态文案
避免字符串拼接，例如：

```ts
'已同步 ' + count + ' 条记录'
```

后续应逐步改为插值形式，例如：

```ts
t('sync.completed', { count })
```

第一阶段可暂不大规模处理动态文案，但设计上要保留该能力。

### 约束新代码
国际化底座建立后，应约束：
- 新增界面文案不得直接硬编码在组件中。
- 新增页面必须通过 `t()` 读取可见文本。

这样旧债不会继续增长。

## 风险与缓解

### 风险 1：改动面失控
表现：
- 一旦开始替换硬编码，容易扩散到大量页面。

缓解：
- 第一阶段严格限制在偏好设置链路。
- 每阶段只处理明确目录或页面集合。

### 风险 2：翻译 key 混乱
表现：
- key 命名无章法，后期查找困难。

缓解：
- 采用模块化命名。
- 以界面语义为 key，而非以视觉位置命名。

### 风险 3：英文不完整导致界面破碎
表现：
- 部分页面显示 key 或空白。

缓解：
- 默认回退中文。
- 优先迁移高频入口页。

### 风险 4：维护成本上升
表现：
- 新增功能时需要同步写双语，团队觉得负担重。

缓解：
- 只要求“新代码走国际化”，旧代码渐进迁移。
- 后续增加字典一致性校验脚本，降低人工检查成本。

## 验证方案

### 功能验证
- 在偏好设置页切换为 English，当前页标题、说明、按钮立即变为英文。
- 切回中文，当前页文案立即恢复中文。
- 刷新页面后语言设置保留。

### 回归验证
- 未迁移页面仍可正常打开。
- 切换语言不会影响已有设置项读写。
- 不引入构建错误或类型错误。

### 建议测试
- 至少执行一次 `npm run build`
- 手动验证设置页语言切换
- 若后续补充工具函数，可增加字典回退与 key 查找的单元测试

## 实施清单
第一阶段实施时按以下顺序进行：

1. 在 `SettingsContext` 中增加 `language` 与 `setLanguage`
2. 建立 `src/i18n/` 目录与最小 `t()` 实现
3. 在偏好设置页增加语言切换 UI
4. 将偏好设置页文案切换为 `t(...)`
5. 补充最小验证并执行构建

## 后续扩展
若未来国际化范围扩大，可继续演进：

- 为 `t()` 增加插值支持
- 为字典增加一致性检查脚本
- 将日期 / 数字格式化统一封装
- 如复杂度继续提升，再评估迁移到 `react-i18next`

## 结论
本次国际化不应被当作“一次性文案大扫除”，而应被设计为“低风险的基础设施接入 + 长周期渐进迁移”。

对当前仓库而言，最稳妥的路径是：
- 先让语言切换在偏好设置链路中跑通
- 建立统一的文案读取出口
- 用中文回退机制保护过渡期体验
- 后续按模块逐步迁移，而不是全库一刀切

该方案满足“切换后立刻生效”的产品要求，同时把大仓库改造风险控制在可验证、可回退的范围内。
