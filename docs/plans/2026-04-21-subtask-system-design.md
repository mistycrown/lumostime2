# Todo 子任务系统设计
日期：2026-04-21

## 目标
- 在现有待办系统上增加“父任务 -> 子任务”的一层层级结构。
- 子任务本身仍是正式待办，能够独立完成、独立排期、独立出现在排期列表与周视图中。
- 父任务与子任务共享执行语境，子任务实时继承父任务的分类、关联活动、默认 scope。
- 第一版尽量复用现有 `TodoItem[]`、排期工具、专注记录与详情编辑链路，不引入第二套任务模型。

## 已确认的约束
- 子任务本身也是正式待办，能单独排期、出现在周视图、关联活动/专注记录。
- 父任务可以独立完成，不要求子任务全部完成后才允许完成。
- 普通待办列表默认折叠显示子任务，详情页中也要体现父子关系。
- 排期和周视图只显示真正有排期的那条任务，不额外带出父任务容器。
- 子任务不能拥有与父任务不同的分类、关联活动、默认 scope；这些字段对父子关系来说是强继承。
- 子任务排期独立，可以单独设置安排日和截止日。
- 子任务不能设置循环。
- 继承采用实时联动。

## 方案对比

### 方案 A：`TodoItem` 内部嵌套 `children: TodoItem[]`
优点：
- 概念直观，父任务对象天然携带整棵子树。

缺点：
- 现有大量代码默认 `todos` 是平铺数组，嵌套后会直接影响列表、排期、统计、搜索、批量管理、同步与日志关联。
- 删除、排序、编辑与持久化都要同时处理树结构，第一版成本过高。

### 方案 B：保持平铺存储，在 `TodoItem` 上增加父子关系字段
优点：
- 与现有 `TodoItem[]` 数据流兼容度最高。
- 子任务依然是一条完整待办，独立排期、独立日志关联都容易保留。
- 列表层做树形组装即可，不必重写存储和同步基础设施。

缺点：
- 列表与详情层需要额外做父子聚合和校验。

### 方案 C：单独新增“父任务 / 项目”实体
优点：
- 模型语义最清晰，父任务和执行项天然分离。

缺点：
- 与当前系统不兼容，因为这里的父任务本身也是正式待办。
- 编辑、迁移、展示、同步都会变复杂，第一版收益不高。

### 结论
采用方案 B：`TodoItem` 仍是唯一待办实体，存储保持平铺，界面层按父子关系组装树。

## 数据模型
在 `src/types.ts` 的 `TodoItem` 上新增可选字段：

```ts
parentTodoId?: string;
childOrder?: number;
```

字段语义：
- 没有 `parentTodoId` 的任务是根任务。
- 有 `parentTodoId` 的任务是子任务。
- `childOrder` 只在同一父任务内部用于稳定排序。

第一版不新增 `children[]`、`depth`、`isCollapsed` 等持久化字段。

## 继承与字段规则

### 子任务实时继承父任务的字段
- `categoryId`
- `linkedCategoryId`
- `linkedActivityId`
- `defaultScopeIds`

规则：
- 子任务详情页中这些字段只读显示，并标注“继承自父任务”。
- 父任务修改这些字段时，需要立即把所有直接子任务同步到相同值。
- 第一版只支持一层结构，所以只需要处理“父 -> 子”的同步。

### 子任务保留独立控制的字段
- `title`
- `note`
- `isCompleted`
- `completedAt`
- `isProgress`
- `totalAmount`
- `unitAmount`
- `completedUnits`
- `scheduledDate`
- `deadlineDate`
- `pin`
- `coverImage`
- `heatmapMin`
- `heatmapMax`

### 循环规则
- 子任务不能设置 `recurrenceRule`。
- 子任务详情页中循环入口隐藏或禁用。
- 如果某条已有循环的待办被转成子任务，需自动清空 `recurrenceRule` 并提示用户。

## 列表与详情交互

### 普通列表
- 普通待办列表只把根任务作为一级列表项渲染。
- 根任务默认折叠子任务，展开后在其下方渲染子任务。
- 子任务视觉上缩进一层，但保留完成、开始专注、打开详情、独立排期等能力。
- 父任务行显示一个简短子任务进度汇总，例如 `3/5`。
- 展开/折叠状态第一版仅保存在界面状态，不写入持久化数据。

### 父任务详情
- 增加“子任务”区域。
- 该区域显示当前父任务下的全部子任务。
- 支持在此区域中新增子任务、打开子任务详情、切换完成状态、调整同父任务内排序。

### 子任务详情
- 顶部明确显示所属父任务，并提供进入父任务详情的入口。
- 分类、关联活动、默认 scope 为只读继承态。
- 安排日、截止日仍可编辑。
- 循环规则不可编辑。

## 新增、删除与排序规则

### 新增子任务
- 入口放在父任务的快速操作或父任务详情页内。
- 创建时自动写入 `parentTodoId`。
- 创建时自动带上父任务当前的 `categoryId`、`linkedCategoryId`、`linkedActivityId`、`defaultScopeIds`。
- 创建结果默认不完成、无循环，可立即设置自己的安排日或截止日。

### 删除子任务
- 与普通待办一致，直接删除。
- 若有历史日志，继续沿用现有“保留历史、解除日志关联”的处理逻辑。

### 删除父任务
- 第一版默认级联删除其全部子任务。
- 删除确认中需要明确提示“将同时删除 N 个子任务”。
- 这样可避免出现失去继承来源的孤儿子任务。

### 排序
- 根任务继续沿用现有列表排序逻辑。
- 子任务仅在同一父任务内部按 `childOrder` 排序。
- 第一版不支持跨父任务拖拽移动，也不支持批量转成子任务。

## 排期、周视图与专注记录

### 排期与周视图
- 排期列表、`今 / 明 / 周` 虚拟分类、周视图仍按“单条任务是否命中日期”来显示。
- 父任务没有排期而子任务有排期时，只显示子任务本身。
- 父任务有排期而子任务没有排期时，只显示父任务本身。
- 子任务允许独立设置 `scheduledDate` 和 `deadlineDate`。

### 专注与日志关联
- 开始专注时，仍关联真正启动的那条任务 ID。
- 如果启动的是子任务，则日志 `linkedTodoId` 指向子任务。
- 因为子任务同步持有父任务的分类、关联活动、默认 scope，所以现有开始专注链路可以继续工作。

## 校验规则
- 子任务不能再拥有子任务，第一版仅支持一层结构。
- 保存时必须阻止把任务挂到自己下面。
- 保存时必须阻止形成循环引用。
- 子任务保存时不允许写入独立的分类、关联活动、默认 scope 变更。
- 子任务保存时不允许保留 `recurrenceRule`。

## 实现边界

### 第一版明确要做
- `TodoItem` 父子关系字段。
- 列表树形折叠展示。
- 父任务详情中的子任务管理区。
- 子任务详情中的父任务信息与继承只读展示。
- 父任务字段变更时对子任务的实时同步。
- 子任务独立安排日、截止日与周视图兼容。
- 父任务级联删除子任务。

### 第一版明确不做
- 孙任务及更深层级。
- 跨父任务拖拽移动。
- 批量转成子任务。
- 父任务聚合排期卡片。
- 子任务独立分类 / 关联活动 / scope。
- 子任务循环规则。
