# 图片索引分组设计

## 背景

当前图片索引把日志附件、待办封面和主题设置素材存放在同一个列表中。重建图片列表、云同步和未引用图片清理因此只能使用同一套引用判断，图片数量增加后既难以解释，也容易误判。

本次把图片按用途分为两组：

- `content`：日志附件与待办封面。
- `theme`：投喂功能和主题设置中的自定义素材，包括自定义贴纸、背景、导航装饰、时间小友图片及其他设置级图片。

图片的分组由上传入口明确指定，不根据文件名推断。自定义贴纸即使被日记使用，其素材归属仍为 `theme`。

## 数据结构与兼容

本地引用索引升级为带版本的分组结构：

```ts
interface ImageManifest {
  version: 2;
  groups: {
    content: string[];
    theme: string[];
  };
}
```

云端图片清单采用相同的分组语义，同时保留合并后的 `images` 字段，供旧版本客户端读取。新版本读取旧版 `{ images: string[] }` 时，将旧条目作为未分类兼容输入；重建或同步后再根据当前数据引用写回两组结构。

所有清单写入都去重，并保持稳定顺序。原图和缩略图沿用当前规则同时登记；没有缩略图的主题素材仅登记原图。

## 建立与重建索引

图片服务提供显式分组登记能力：

- 日志、相机日志和待办封面上传后登记到 `content`。
- 投喂页和主题设置上传后登记到 `theme`。
- 删除图片时从两组中一并移除原图和缩略图。

数据管理中的“修复图片列表”分别重建两组：

- `content` 只扫描 `logs[].images` 和 `todos[].coverImage`。
- `theme` 扫描外观/主题设置、自定义贴纸元数据及其他设置级图片引用。

重建结果只保留本地实际存在的文件，避免索引继续保留失效条目。

## 同步

同步上传时分别构建内容图片和主题图片引用，并以分组清单作为上传依据。实际文件上传仍可复用现有批量上传流程，但统计和清单保留分组信息。

同步下载时读取云端分组清单，并分别与恢复后的内容数据和外观数据求交集。若云端只有旧版合并清单，则用恢复后两组引用集合筛选，保证向后兼容。

云端一致性检查继续使用合并文件集合对比实际文件，同时从分组清单生成合并集合，不改变文件级修复行为。

## 清理

未引用检查先建立两套引用集合，再按索引分组选择对应策略：

- `content` 图片仅在日志和待办中验证。
- `theme` 图片仅在主题设置和投喂素材元数据中验证。
- 旧版未分类条目分别尝试匹配两套集合；两边都未命中才视为未引用。
- 本地存在但索引缺失的文件，也分别与两套当前引用集合匹配；均未命中才进入清理列表。

清理报告分别显示两组的索引数、有效引用数和待清理数，执行清理后同步更新分组索引。

## 验证

- 图片索引的旧数组格式可以安全读取和迁移。
- 日志/待办上传登记为 `content`，投喂/主题上传登记为 `theme`。
- 重建后的两组只包含各自数据源仍引用且本地存在的文件。
- 清理不会跨组误判引用；真正未被对应数据源引用的图片会进入清理列表。
- 同步上传、下载和云端一致性检查兼容新旧清单格式。
- 运行相关 Vitest 用例与 `npm run build`。
